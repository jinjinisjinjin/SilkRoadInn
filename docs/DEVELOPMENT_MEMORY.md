# 项目复盘与可复用工作经验

> 这不是产品规则、功能清单或交接说明，而是我在项目开发中踩过的坑，以及可以带到下一份工作的判断方法。具体数值、点位和玩法应留在产品文档里；这里只记录“为什么会出问题、以后怎样更早发现”。

## 1. 先定义体验完成，再定义程序完成

### 踩过的坑

程序在某个事件触发后立刻推进状态，看起来逻辑已经完成，但用户还在观看动画、阅读内容或与当前对象互动。系统已经进入下一步，用户却没有完成上一段体验，于是出现人物突然消失、画面跳转、反馈被打断等问题。

### 可复用经验

- “事件触发”不等于“体验结束”。
- 条件满足只代表用户“可以进入”，不代表用户“此刻想进入”；自动引导优先使用非阻断高亮，模态页面应留给用户主动触发。
- 状态推进应绑定用户能感知的结束点，例如动画退场、内容关闭或明确确认，而不是绑定最早发生的技术事件。
- 开发复杂交互前，先写一条用户时间线，再写状态机。

### 下次检查

对每个自动推进动作都问一句：用户此刻是否已经看完、理解完、操作完？如果答案不是确定的“是”，就不要切换状态。

## 2. 动画只能表现状态，不能代替状态

### 踩过的坑

画面在动画期间显示了新状态，动画结束或页面重渲染后却恢复旧样子。根因是视觉效果只存在于临时 DOM 或 CSS 类中，没有由持久数据重新生成。

### 可复用经验

- 动画是状态变化的表现层，不是状态本身。
- 所有需要刷新后仍成立的结果，都必须写入唯一数据源。
- 每次渲染都应能只根据数据重建正确画面，而不依赖上一次动画留下的元素。

### 下次检查

完成操作后刷新页面、切换页面再返回、重新载入旧存档。如果结果不能稳定复现，说明状态与表现还没有分离。

## 3. 局部美术替换最怕“贴图感”

### 踩过的坑

把新画面直接覆盖到旧画面上，边缘像拼图；小物件虽然坐标正确，却因为比例、遮挡、光线或接触面不对，看起来悬在空中。

### 可复用经验

- 场景合成不能只看坐标，还要同时检查比例、接触面、前后遮挡、光向和色温。
- 新旧画面的连接处要使用羽化、不规则边缘或环境遮挡，避免硬矩形切口。
- 小物件应先确定“它被什么承托”，再决定位置；地面、桌面、屋顶对应不同的透视和阴影。
- 真实比例与可发现性冲突时，先保持空间可信，再用闪光、动效或镜头引导提高可见度。

### 下次检查

缩小到用户真实观看尺寸，暂时关闭提示气泡，只看物件是否仍像属于这个场景，而不是后贴上去的图标。

## 4. 反馈层级不能互相抢注意力

### 踩过的坑

答案解析、奖励入口、按钮和说明文字被放在同一张卡片中。用户不知道应该继续阅读、滚动还是先领奖，原本愉快的奖励变成了阅读任务。

### 可复用经验

- 同一时刻只让一个目标成为视觉主角。
- 过渡反馈要与信息量匹配；如果只需表达一次状态升级，短动画比完整中间页更清晰，避免为了仪式感增加停顿和点击。
- 跨多轮确认过的关键决策不能只依赖对话上下文：长任务压缩上下文后，早期约定可能不进入摘要。遇到后来又被改动的数值或规则，应先查提交历史与既有决定，再判断当前实现是否仍代表用户意图。
- 即时奖励适合短暂、独立、自动完成的动效；深度内容适合留在原页面供用户按自己的节奏阅读。
- 能自动完成且没有选择意义的步骤，不应要求用户再点击一次。
- 奖励物本身已经能表达价值时，少加背景板、标题和说明，避免包装压过内容。

### 下次检查

让第一次体验的用户在画面出现后立刻回答“现在最应该做什么”。如果不同用户给出不同答案，说明层级仍然混乱。

## 5. 数值必须符合用户的心智单位

### 踩过的坑

系统内部习惯用总数计算，界面却使用可合成的等级物件表达价值。直接发放大额数字虽然计算正确，却破坏了用户对物品成长和稀缺度的理解。

### 可复用经验

- 奖励和成本不只是一串数，它们属于一套用户已经学会的价值语言。
- 新系统应复用既有物件、等级和库存通道，避免创造第二套相互竞争的经济表达。
- 早期奖励优先给低阶、可理解、可继续成长的东西；稀有奖励靠概率和组合制造惊喜。

### 下次检查

不要只审表格中的总价值，还要检查玩家实际看到的物件数量、等级分布和进入库存后的下一步用途。

## 6. 内容变短通常不是文案问题，而是结构问题

### 踩过的坑

大量剧情只有一句功能性台词。单句本身并不差，但它同时承担背景、冲突、人物动机和行动指令，结果更像提示语而不是故事。

### 可复用经验

- 先做全量篇幅审计，判断是个别遗漏还是系统性缺少内容标准。
- 一段短剧情至少需要：可见问题、人物诉求、具体细节、一次犹豫或分歧、行动决定、自然出口。
- 延长篇幅不能靠重复信息；每一页必须推动事实、关系或情绪中的至少一项。
- 先做一段完整样板，确认人物声音和节奏，再按章节扩写，避免批量生成同构台词。
- 结果回响应比行动前的故事短，避免完成任务后又被长剧情拦住。

### 下次检查

删掉角色名后，如果所有人的话都可以互换，说明人物声音还没有建立；删掉任意一页后若毫无影响，说明那一页没有承担叙事功能。

## 7. 教育内容要让证据层级可见

### 踩过的坑

为了让内容更好读，把史料、合理推测和游戏创作写成同一种确定口吻。知识看起来更完整，却容易让用户把虚构细节当成历史事实。

### 可复用经验

- 明确区分可靠材料、参考复原和叙事虚构。
- 史料图片不只是装饰，应与当前问题或解析直接相关，并保留出处。
- 产品内部的取材方法不必全部展示给玩家；玩家需要的是清楚、自然、可核对的结论。
- 教育内容应该奖励好奇心，而不是把游戏操作变成考试。

### 下次检查

逐句追问：这句话的确定程度来自哪里？如果来源只能支持更弱的表达，就降低口吻强度或明确标注推测。

## 8. 大体积项目需要生产管线，不是事后压缩

### 踩过的坑

把源码体积、仓库体积和线上产物体积混为一谈，以为上传平台会自动处理所有图片，或者为了部署临时删除仍在使用的素材。

### 可复用经验

- 明确区分母版资产、运行时资产和生产构建产物。
- 图片格式转换、质量压缩、无用文件排除和引用改写应由可重复的构建脚本完成。
- 构建产物应能随源码重新生成，不要靠人工挑文件上传。
- 部署前关注最终产物、单文件大小和请求数量，而不只看工作目录总大小。

### 下次检查

在干净环境执行一次完整构建，记录输入体积、输出体积、转换数量和失败条件；任何只能在某台电脑手动完成的步骤都还不算管线。

## 9. 多窗口并行时，路径和版本比速度更重要

### 踩过的坑

多个窗口看似在开发同一个项目，实际可能位于不同目录、分支或临时工作树。每个改动单独都正确，合并时却出现重复实现、旧代码覆盖新代码或用户看到的页面并非刚修改的版本。

### 可复用经验

- 开工前确认仓库绝对路径、分支、远程地址和实际预览目录。
- 一个功能只设一个事实来源；并行任务按边界拆分，不让多人同时改同一条状态链。
- 临时工作树完成后及时合并和清理，避免它被误认成长期主项目。
- 给静态资源加版本标识，排除缓存造成的“改了但没变化”。

### 下次检查

每次交付前同时检查 `pwd`、当前分支、Git 状态、页面实际加载的资源版本和服务进程的工作目录。

## 10. 截图标注需要转成稳定坐标

### 踩过的坑

根据截图中的“向左一点、向下一厘米”直接修改像素。换一台设备或改变缩放后，物件又偏离目标位置。

### 可复用经验

- 截图标注先用于确认视觉意图，再换算成相对场景的标准化坐标。
- 位置、尺寸和旋转应集中配置，避免散落在临时样式覆盖中。
- 先校准场景基准尺寸和裁切方式，再根据标注微调。

### 下次检查

至少在两种窗口尺寸下复查，并保存“目标承托物”而不只是最终像素值。

## 11. 验收必须覆盖整条链路

### 踩过的坑

单个页面或动画截图看起来正确，但从前一步进入、退出再返回、使用旧存档时出现问题。局部验收掩盖了状态之间的连接错误。

### 可复用经验

- 功能测试要从触发条件开始，一直走到下一稳定状态。
- 同时验证首次进入、重复进入、刷新恢复、旧存档迁移和快速连续操作。
- 自动检查负责语法、数据完整性和构建；真实浏览器负责节奏、遮挡、点击范围和视觉连续性，两者不能互相替代。
- 无法完成视觉验收时要明确说明，不用“构建成功”代替“体验正确”。

### 下次检查

为核心功能写一条固定验收旅程，并在重大修改后从头走完，而不是只打开修改发生的最后一个画面。

## 12. 把反馈翻译成设计原则

### 踩过的坑

每次只按照一句反馈移动位置或增加按钮，虽然解决了眼前问题，却没有提炼出共同原因，同类错误不断在其他页面重现。

### 可复用经验

收到反馈后分四层记录：

1. 用户看到的现象。
2. 用户真正受阻的体验目标。
3. 造成问题的系统性原因。
4. 能约束后续设计的通用原则。

例如，“这个东西像飘在空中”不仅是坐标错误，更说明场景物件必须有承托关系；“不知道该看解析还是领奖”不仅是排版问题，更说明反馈层级在竞争。

## 13. 复盘记录模板

以后每次值得沉淀的问题，只追加以下内容：

```text
日期：
项目阶段：
用户看到的现象：
根因：
最后采用的方案：
可以迁移到其他项目的经验：
下次如何更早发现：
```

只记录具有迁移价值的判断。具体坐标、数值、剧情台词、资源名和当前玩法规则留在对应设计文档或代码中。
